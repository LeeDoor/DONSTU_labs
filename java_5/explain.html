Generics в Java: аналогии с шаблонами C++

Если вы знаете templates в C++, идея уже знакома: написать один алгоритм или контейнер, который работает с несколькими типами. Java generics решают похожую задачу, но устроены иначе — особенно во время компиляции и выполнения программы.

1. Зачем нужны обобщения

Допустим, нужен список целых чисел, затем список строк. Без обобщений пришлось бы писать отдельный класс для каждого типа либо хранить всё как Object и вручную приводить тип при чтении. Второй вариант компилируется даже при ошибочном смешивании данных, а ошибка может проявиться только при выполнении. 

// Без generics: тип элемента теряется
List values = new ArrayList();
values.add("привет");
Integer number = (Integer) values.get(0); // ошибка во время выполнения

// С generics: компилятор знает тип элементов
List<String> words = new ArrayList<>();
words.add("привет");
String word = words.get(0); // приведение не требуется

List<String> читается как «список, элементы которого — строки». Компилятор проверяет это ограничение: например, попытка добавить туда Integer будет ошибкой компиляции.

2. Похожий синтаксис, но не тот же механизм, что в C++

ТемаC++ templatesJava generics
Пример параметра типа template<typename T> class Box class Box<T>
Как появляется код Компилятор обычно инстанцирует код для конкретных аргументов шаблона. Компилятор проверяет типы, затем в основном стирает параметры типов; во время выполнения нет отдельной версии класса для каждого T.
Что может быть параметром Типы и, в зависимости от шаблона, значения времени компиляции. Параметр generics — ссылочный тип. int напрямую нельзя, но компилятор автоматически упаковывает его в Integer.
Какие операции допустимы Шаблон может использовать выражения, если они допустимы для конкретного T; это проверяется при инстанцировании. В обобщённом коде доступно только то, что гарантируют границы типа (bounds).
Главное отличие: Java generics в первую очередь дают статическую проверку типов и удобный API. Это не механизм генерации специализированного машинного кода, как обычно ожидают от C++ templates.

3. Обобщённый класс и несколько параметров

Параметр пишется в угловых скобках после имени класса. По соглашению используют короткие имена: T (тип), E (элемент), K (ключ), V (значение). 

public class Pair<T, U> {
    public final T first;
    public final U second;

    public Pair(T first, U second) {
        this.first = first;
        this.second = second;
    }
}

Pair<Integer, String> result = new Pair<>(42, "ответ");
Integer index = result.first;
String label = result.second;

Здесь T и U независимы: первое поле может быть числом, второе — строкой. Оператор <> при создании объекта называется «ромб» (diamond): справа типы выводятся из левой части.

Для примитивов используются классы-обёртки: Integer вместо int, Double вместо double, Boolean вместо boolean. Автоупаковка позволяет обычно писать List<Integer> xs = ...; xs.add(5); без явного вызова конструктора обёртки.

4. Обобщённый метод

Метод может иметь собственный параметр типа, даже если его класс необобщённый. Параметры метода объявляются перед возвращаемым типом: 

import java.util.Arrays;
import java.util.List;

public static <T> T first(List<T> items) {
    if (items.isEmpty()) {
        throw new IllegalArgumentException("список пуст");
    }
    return items.get(0);
}

String word = first(Arrays.asList("один", "два"));
Integer number = first(Arrays.asList(10, 20));

Компилятор обычно сам выводит T из аргументов. У статического метода нет доступа к параметру типа экземпляра класса: если он нужен, объявите собственный параметр непосредственно у метода, как в примере.

5. Границы параметра: что разрешено делать с T

В отличие от шаблона C++, Java не позволяет просто вызвать на неизвестном T произвольный метод и отложить проверку до подстановки типа. У компилятора должны быть гарантии. Их задаёт ограничение extends: 

class Box<T extends Number> {
    private T value;

    double asDouble() {
        return value.doubleValue(); // метод гарантирован типом Number
    }
}

Ключевое слово extends используется и для интерфейсов: <T extends Comparable<T>>. Несколько границ записываются через &, например <T extends Number & Comparable<T>>.

Такая граница похожа на требование к типу шаблона, но Java требует выразить его через базовый класс или интерфейс. Она не позволяет передавать примитивный int; передавайте Integer.

6. Инвариантность: почему List<Cat> — не List<Animal>

Даже если Cat наследуется от Animal, List<Cat> не является подтипом List<Animal>. Если бы это было разрешено, в список кошек можно было бы положить собаку через ссылку на список животных. 

List<Cat> cats = new ArrayList<>();
// List<Animal> animals = cats; // не компилируется: так безопаснее

Это называется инвариантностью. Она действует и для пользовательских обобщённых классов, а не только для коллекций.

7. Wildcards и правило PECS

Если метод должен принять коллекцию нескольких совместимых типов, вместо конкретного параметра типа можно использовать wildcard ?. Важны два варианта:

  • ? extends Animal — «какой-то неизвестный тип Animal или его потомок». Из такой коллекции безопасно читать Animal, но нельзя добавлять туда конкретную кошку: фактическая коллекция может быть списком собак.
  • ? super Cat — «какой-то неизвестный тип Cat или его предок». В неё безопасно добавлять Cat; при чтении гарантирован только Object. 
static double total(List<? extends Number> numbers) {
    double sum = 0;
    for (Number n : numbers) {
        sum += n.doubleValue(); // читаем как Number
    }
    return sum;
}

static void addCats(List<? super Cat> destination) {
    destination.add(new Cat()); // Cat можно записать и в List<Animal>
}
PECS: Producer Extends, Consumer Super. Если параметр метода только поставляет значения для чтения — рассмотрите ? extends T. Если принимает значения для записи — ? super T. Это практическое правило, а не требование применять wildcard везде.

8. Стирание типов (type erasure)

Java проверяет аргументы типов при компиляции, затем выполняет стирание: в байткоде параметры типов заменяются их верхней границей (обычно это Object). Компилятор вставляет необходимые приведения при чтении. Для ограниченного параметра <T extends Number> стирается до Number, а не до Object.

Практические последствия стирания:

  • new T() и new T[10] обычно запрещены: во время выполнения неизвестно, какой именно T создавать.
  • value instanceof List<String> запрещено: объект во время выполнения не хранит аргумент String.
  • Нельзя объявить две перегрузки, различающиеся только параметрами типа, например f(List<String>) и f(List<Integer>): после стирания обе имеют одинаковую сигнатуру.
  • В большинстве случаев нельзя создать массив параметризованного типа, например new List<String>[10]. Обычно используйте коллекцию.

Это отличие от обычной модели C++ templates: в Java параметры типов предназначены прежде всего для проверок компилятора, а не для создания отдельных runtime-типов Box<String> и Box<Integer>.

9. Raw types — старый код без аргумента типа

Запись List без <...> называется raw type. Она оставлена для совместимости со старым Java-кодом. Raw type отключает часть проверок компилятора и может вернуть проблему с ошибочным приведением типов. В новом коде указывайте параметр типа: List<String>; если тип пока неизвестен, часто подходит List<?>.

10. Короткий ориентир

  1. Используйте Class<T>, когда сам класс хранит или обрабатывает значения одного типа.
  2. Используйте <T> у метода, когда тип связывает аргумент с результатом или между несколькими аргументами.
  3. Задавайте extends-границу, если обобщённому коду нужны методы базового типа или интерфейса.
  4. Помните об инвариантности; для гибких параметров метода изучите ? extends T и ? super T.
  5. Не рассчитывайте на доступ к аргументу типа во время выполнения: Java стирает его.
В исходниках этой лабораторной идеи видны в Pair<T, U>, GPairBag<T, U>, DList<T, U> и HashTable<T, K>.
